**Концептуальная архитектура открытия депозитов онлайн (MVP)**

### ADR-001

### Автор: DevPastet

### Дата: 12.10.2026

### Статус: предложено

---

### Контекст

Банк «Стандарт» хочет привлечь более молодых клиентов и для этого выводит депозиты и накопительные счета в онлайн-каналы. Сейчас депозит можно открыть только в отделении. Что мешает сделать продукт цифровым:

- Ставки ведутся в XLS-файлах и пересылаются по почте. Ни сайт, ни интернет-банк не могут получить их программно.
- Согласование ставки — ручная переписка фронт-офиса, бэк-офиса депозитов и отдела кредитов. Она занимает от 20 минут до часа.
- Интернет-банк — монолит на платформе подрядчика (.NET Framework 4.5). Он работает напрямую с БД АБС, несовместим с Kafka, развёрнут на одной группе серверов.
- БД АБС перегружена и масштабируется только вертикально.

Цель MVP на 6 месяцев: клиент подаёт заявку на депозит на сайте или в интернет-банке, заявку по-прежнему обрабатывает бэк-офис. Цель на год — открытие депозита без участия сотрудников — в это решение не входит, но решение не должно ей мешать.

Требования собраны в [Task2/FURPS.md](../Task2/FURPS.md). Ниже приведены те из них, которые определяют архитектуру.

### Нефункциональные требования

| № | Требование |
|---|------------|
| NFR-1 | Доступность сервисов нового процесса 99,9% в режиме 24/7 |
| NFR-2 | При отказе основного ЦОД сервисы депозитного контура остаются доступны и выдерживают нагрузку. RPO для заявок 0, RTO не более 15 минут |
| NFR-3 | Время отклика клиентских операций: 95-й перцентиль не более 300 мс на чтение и 500 мс на подачу заявки. Справочные данные загружаются не дольше 200 мс |
| NFR-4 | Новый процесс не создаёт синхронной нагрузки на БД АБС. Недоступность АБС не мешает смотреть ставки и подавать заявки |
| NFR-5 | Сервисы интернет-банка масштабируются горизонтально, запросы распределяются между экземплярами и ЦОД. АБС масштабируется только вертикально |
| NFR-6 | Принятая заявка не теряется и не дублируется |
| NFR-7 | Трафик шифруется по TLS не ниже 1.2 на периметре и между системами. Персональные данные хранятся в зашифрованном виде |
| NFR-8 | Сотрудники депозитов и кредитов не имеют доступа к данным друг друга |
| NFR-9 | Используются технологии, уже имеющиеся в банке: .NET, MS SQL, Oracle, Java, PHP, React.js. Для очередей — Kafka |
| NFR-10 | Доработок ядра платформы интернет-банка силами подрядчика нет или они минимальны. Бизнес-функционал реализует команда банка |
| NFR-11 | Интерфейсы соответствуют системе дизайна компании |
| NFR-12 | Для новых сервисов и интеграций есть документация: OpenAPI, схемы событий, ADR |
| NFR-13 | Задержка между утверждением ставки в АБС и её появлением в каналах не более 5 минут |

#### Суть решения

1. **АБС становится мастер-системой ставок.** Расчёт и утверждение ставок переносятся из Excel в новый модуль АБС.
2. **Рядом с монолитом интернет-банка появляется депозитный контур** из новых сервисов на современном .NET. Монолит остаётся точкой входа и отвечает за аутентификацию.
3. **Депозитный контур и АБС общаются только асинхронно через Kafka.** У онлайн-каналов есть собственная копия ставок.
4. **Сайт и система кол-центра подключаются к тому же контуру.** Сайт использует REST API, система кол-центра читает события из Kafka.

#### Контейнеры интернет-банка

| Контейнер | Технологии | Статус | Назначение |
|-----------|------------|--------|------------|
| Веб-приложение интернет-банка | ASP.NET MVC 4.5, платформа подрядчика | Дорабатывается | Монолит. Аутентификация, счета, платежи. Добавляется раздел «Депозиты» на точках расширения платформы и выдача короткоживущего JWT для вызова новых сервисов. Счета клиента для выбора в заявке берутся из уже существующей функции монолита |
| БД интернет-банка | MS SQL Server | Без изменений | Данные монолита |
| API-шлюз | Nginx | Новый | Единая точка входа в новые сервисы для монолита и сайта. Завершает TLS, проверяет JWT, ограничивает частоту запросов, балансирует нагрузку между экземплярами и ЦОД |
| Сервис депозитов | ASP.NET Core (.NET 8), C# | Новый | Витрина продуктов и ставок, персональные ставки, приём заявок из интернет-банка и лидов с сайта, статусы заявок. Не хранит состояние в памяти, работает в двух ЦОД |
| БД сервиса депозитов | MS SQL Server, Always On | Новый | Заявки, статусы, копия ставок, таблица outbox. Синхронная репликация между ЦОД |
| Кэш | Redis | Новый | Ставки и справочники продуктов для быстрых ответов, одноразовые коды с ограниченным временем жизни |
| Сервис подтверждений | ASP.NET Core (.NET 8), C# | Новый | Генерирует и проверяет одноразовые коды, отправляет СМС через СМС-шлюз. Не зависит от депозитов, будет переиспользован для заявок на кредит |

#### Контейнеры АБС

| Контейнер | Технологии | Статус | Назначение |
|-----------|------------|--------|------------|
| БД АБС | Oracle, PL/SQL | Дорабатывается | Новый модуль «Ставки по депозитам»: показатели, расчёт, утверждение, специальные и персональные ставки. Очередь онлайн-заявок. Таблицы staging для входящих заявок и outbox для исходящих событий. Разграничение доступа между депозитами и кредитами на уровне ролей и представлений |
| Клиент АБС | Delphi | Дорабатывается | Формы ведения ставок для двух бэк-офисов, очередь онлайн-заявок, форма согласования специальной ставки |
| Интеграционный адаптер АБС | Java 17, Spring Boot, Spring Kafka | Новый | Единственная точка связи АБС с Kafka. Читает заявки и пишет их в staging-таблицы пачками с ограничением скорости. Читает outbox и публикует ставки и статусы. Разрабатывают Java-специалисты команды АБС |

#### Остальные системы

| Система | Статус | Изменения |
|---------|--------|-----------|
| Шина событий Apache Kafka | Новая | Кластер, растянутый на два ЦОД. Топики: `deposit.rates`, `deposit.personal-rates`, `deposit.applications`, `deposit.leads`, `deposit.application-status` |
| Сайт | Дорабатывается | Страница депозитов со ставками и форма заявки. Бэкенд на PHP вызывает API-шлюз по HTTPS |
| Система кол-центра | Дорабатывается | Потребитель топика `deposit.leads`, создание задачи на обзвон. Реализуется через механизм расширений платформы |
| СМС-шлюз | Без изменений | Принимает запросы от сервиса подтверждений и от АБС |

#### Ключевые сценарии

**Публикация ставок (UC-8).** Менеджер утверждает ставки в АБС. Процедура PL/SQL в той же транзакции пишет событие в таблицу outbox. Адаптер читает outbox и публикует событие в `deposit.rates`. Сервис депозитов обновляет свою копию ставок в БД и кэш. Сайт и интернет-банк читают ставки только из сервиса депозитов, АБС в этом запросе не участвует.

**Заявка в интернет-банке (UC-4, UC-5, UC-10).** Монолит аутентифицирует клиента и отдаёт страницу раздела с JWT. Страница запрашивает ставки через API-шлюз. При подаче заявки сервис депозитов запрашивает код у сервиса подтверждений, тот отправляет СМС. После проверки кода сервис депозитов в одной транзакции сохраняет заявку и запись outbox, затем публикует событие в `deposit.applications`. Клиент сразу получает ответ «Заявка принята». Адаптер АБС переносит заявку в staging-таблицу, задание PL/SQL помещает её в очередь бэк-офиса. Изменения статуса возвращаются через `deposit.application-status`.

**Заявка на сайте (UC-1, UC-2, UC-3).** Сайт передаёт Ф. И. О. и телефон в сервис депозитов через API-шлюз. Сервис публикует событие в `deposit.leads`. Система кол-центра создаёт задачу на обзвон. Дальше работает существующий процесс: обращение в АБС, предварительное определение ставки бэк-офисом, СМС клиенту, визит в отделение для идентификации.

**Уведомления (UC-9).** СМС о подтверждённой ставке и об открытии депозита отправляет АБС существующим механизмом. Новая интеграция для этого не строится.

#### Обоснование ключевых решений

| Решение | Почему так |
|---------|------------|
| Ставки ведутся в АБС | В АБС уже есть данные о портфеле и кредитном риске, раздельные разделы для депозитов и кредитов, привычный сотрудникам интерфейс. Процесс согласования ставки уже частично проходит через АБС |
| Отдельные сервисы вместо доработки монолита | .NET Framework 4.5 несовместим с Kafka, обновление ядра зависит от подрядчика, монолит не масштабируется горизонтально. Новый контур можно развернуть в двух ЦОД, не трогая платежи |
| Асинхронный обмен через Kafka | БД АБС перегружена. Очередь сглаживает пики и позволяет принимать заявки при недоступной АБС. Обработка заявки бэк-офисом всё равно не мгновенная |
| Адаптер на Java и паттерн outbox | В команде АБС есть Java-специалисты. Outbox гарантирует, что событие публикуется тогда и только тогда, когда изменение зафиксировано в АБС. Нагрузка на Oracle — одно чтение небольшой таблицы по расписанию |
| Свой сервис подтверждений | СМС-функционал в ядре платформы требует доработки подрядчиком. Отдельный сервис пишет команда банка, он пригодится для кредитов |
| .NET 8 и MS SQL для новых сервисов | Команда интернет-банка пишет на C# и работает с MS SQL. Новым оказывается только фреймворк, язык и СУБД остаются теми же |
| Сайт ходит по REST, а не в Kafka | Для PHP это простой и привычный способ. Сайту нужен синхронный ответ со ставками |
| СМС о статусах отправляет АБС | Механизм уже работает. Объединение всех уведомлений в одном сервисе отложено на этап после MVP |

#### Развёртывание и отказоустойчивость

- Сервис депозитов, сервис подтверждений и API-шлюз работают одновременно в обоих ЦОД, не менее двух экземпляров в каждом. Запросы распределяет балансировщик.
- БД сервиса депозитов — группа доступности Always On с синхронной репликой во втором ЦОД.
- Кластер Kafka растянут на два ЦОД, фактор репликации 3, запись подтверждается большинством реплик.
- Redis работает с репликой и автоматическим переключением. При потере кэша ставки читаются из БД сервиса.
- Монолит интернет-банка в MVP остаётся в прежней схеме с резервным ЦОД. Это ограничение описано ниже.

#### Команды и зоны ответственности

| Команда | Что делает |
|---------|------------|
| Команда интернет-банка, банк | Сервис депозитов, сервис подтверждений, их БД и кэш |
| Подрядчик интернет-банка | Раздел «Депозиты» в интерфейсе монолита, выдача JWT. Ядро платформы не меняется |
| Команда АБС | Модуль ставок, очередь онлайн-заявок, формы Delphi, интеграционный адаптер |
| Команда сайта | Страница депозитов и форма заявки |
| Подрядчик кол-центра и Java-специалисты АБС | Приём заявок с сайта в системе кол-центра |
| Управление IT, инфраструктура | Kafka, API-шлюз, балансировка, сертификаты, мониторинг, конвейер поставки |
| Команда цифровой трансформации | Контракты API и событий, координация, приёмка |

### Альтернативы

| № | Альтернатива | Плюсы | Почему отклонена |
|---|--------------|-------|------------------|
| 1 | Реализовать депозиты внутри монолита интернет-банка с прямой записью в БД АБС, как сделаны платежи | Быстрее всего, знакомая схема, нет новых технологий | Увеличивает нагрузку на перегруженную БД АБС. Привязывает к подрядчику и к .NET Framework 4.5. Не даёт доступности 99,9% и работы в двух ЦОД. Сайт и кол-центр всё равно требуют отдельных интеграций |
| 2 | Синхронный REST API поверх АБС, который вызывают интернет-банк и сайт | Простая модель, всегда свежие данные, нет шины | Доступность и скорость онлайн-каналов становятся равны доступности и скорости АБС. Пики нагрузки приходят прямо в Oracle. Противоречит требованию избегать прямой работы с API АБС |
| 3 | Вести ставки в новом отдельном сервисе, а не в АБС | Независимость от команды АБС, современный стек | Данные для расчёта (портфель, кредитный риск) находятся в АБС, их пришлось бы выгружать. Сотрудникам нужен новый интерфейс и обучение. Разграничение доступа пришлось бы строить заново. Для MVP на 6 месяцев риск слишком велик |
| 4 | Полностью переписать интернет-банк на микросервисы | Снимает все ограничения платформы | Не укладывается в 6 месяцев. Высокий риск для работающих платежей. Задача требует микросервисов только в рамках депозитов |
| 5 | Захват изменений из журналов Oracle (CDC, Debezium) вместо outbox и адаптера | Не нужно менять процедуры PL/SQL | Наружу попадает внутренняя структура таблиц АБС вместо бизнес-событий. Нужны дополнительные настройки и лицензии Oracle, в банке нет экспертизы. Входящий поток заявок всё равно требует адаптера |
| 6 | Доработать СМС-функционал в ядре платформы силами подрядчика | Единый механизм СМС в интернет-банке | Зависимость от сроков и стоимости подрядчика. Прямо названа нежелательной |
